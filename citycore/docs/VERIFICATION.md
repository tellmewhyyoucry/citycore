База для проверки: **MariaDB 10.11.14**, отдельная локальная установка, InnoDB. Runtime: **Node v24.19.0 / Linux**. Конфигурация Docker использует MariaDB 11.4, Node 22; эти контейнеры в среде подготовки не запускались. Поэтому проверка локальной MariaDB не заменяет проверку Docker-развёртывания.

Интеграционные тесты работают с настоящими таблицами и конкурентными транзакциями, не с mock или SQLite. Проверяются:

- одна запись при 12 одновременных повторах пополнения;
- встречные переводы и сохранение балансов;
- защита от параллельного перерасхода;
- откат списания при переполнении кошелька получателя;
- конфликт UUID при изменении параметров;
- две попытки передать последний предмет;
- откат при полной стопке получателя и превышении общего веса;
- покупка, продажа, употребление еды;
- доставка до получения посылки/раньше времени/из другой точки/без машины;
- повторная выплата, в том числе с другим UUID;
- выход, повторный вход, отмена смены и сохранение вещей;
- истечение старой сессии после нового входа;
- дистанция, dimension, неизвестный получатель и нехватка денег;
- расход аптечки без повторного эффекта при replay;
- чтение новой DB-сессией и повторный запуск миграции;
- HTTP health, bridge/admin-ключи, отсутствие авторизации, login/action/logout.

Логи: `build.log`, `test.log`, `test-integration.log`, `bench.log`.

## Нагрузочный опыт

Детали: `benchmark.json`. Выполнено 1000 переводов в 10 параллельных рабочих циклах на 20 персонажах. Каждый цикл переводит $1 между своей парой туда и обратно. Измеряются валидация, Knex, блокировки и запись в MariaDB. Подготовка аккаунтов не входит в замер.

| Метрика | Значение |
|---|---:|
| Продолжительность измеряемого участка | 1913 мс |
| Пропускная способность | 523 операции/с |
| p50 | 14,73 мс |
| p95 | 39,65 мс |
| p99 | 110,23 мс |
| Ошибки | 0 |

Это короткий локальный опыт на конкретном CPU (модель записана в JSON), с независимыми парами и пулом из 10 DB-соединений. Он не моделирует тысяч игроков, сетевую задержку, HTTP API, синхронизацию GTA, длительный рост таблиц или общий «горячий» счёт. Результат показывает воспроизводимый метод проверки и сохранение инвариантов, а не production-SLA. Для анализа узких мест нужны отдельные прогоны с изменением конкуренции, размером данных и профилированием SQL.

## Требует проверки в GTA V на Windows

Серверные/клиентские пакеты RAGE MP собраны, но реальная GTA V в среде подготовки отсутствует. Не отмечай пункты ниже выполненными до игрового прогона:

- [ ] Вход и регистрация видны в CEF, поля получают фокус.
- [ ] F2 и Esc корректно переключают курсор и управление.
- [ ] Спавн у склада находится на земле, маркеры видимы.
- [ ] Фургон появляется без пересечения с объектами, игрок садится за руль.
- [ ] Получение посылки и маршрут работают.
- [ ] Все три точки доставки доступны по дороге.
- [ ] После доставки зарплата и XP отражаются в UI.
- [ ] Следующий заказ и отмена смены работают.
- [ ] Смерть, уничтожение фургона и выход отменяют смену.
- [ ] Банк и магазин доступны в указанных координатах.
- [ ] Два игрока могут передавать предметы рядом; удалённая передача отклоняется.
- [ ] Аптечка меняет здоровье; её аварийное восстановление имеет ограничение из ARCHITECTURE.md.
- [ ] После перезапуска API и сервера сохранённые данные читаются.
- [ ] Записано демонстрационное видео.

Подключение Redis, запуск GitHub Actions в удалённом репозитории и контейнерное развёртывание также требуют отдельной проверки в целевом окружении. Включён код и конфигурация; отсутствующий результат не заменён утверждением об успешном запуске.
